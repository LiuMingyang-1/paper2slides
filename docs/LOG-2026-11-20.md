## 2. 技术判断（面试核心论点）

| # | 判断 | 依据 |
|---|---|---|
| J1 | **单篇论文不用 RAG 解决"装不下"**，整篇放进上下文；检索只用于证据定位、逐页收窄上下文、核验 | 实测：整篇 BERT 13.4k tokens 一次输入，模型理解正确、引用正确，只花 1.6 额度（[PLATFORM-PROBE.md](PLATFORM-PROBE.md)） |
| J2 | **混合检索**：BM25（数字/术语/数据集名）+ 向量（语义）+ RRF 融合；单篇几百块，浏览器内存暴力算，不用向量库 | 按规模选型。学术事实核心是精确词，向量对其不敏感 |
| J3 | **向量检索默认关闭**，作为可选增强 | 实测 `llm.embed` 每次调用至少 1 额度且最多 64 条，一篇论文向量化 5–9 额度，比全部生成调用还贵 |
| J4 | 按论文结构切块（章节→段落），表格/图注/公式单独成块，**剔除参考文献与页眉页脚** | 参考文献不剔除会污染召回 |
| J5 | **排版：模型只选版式和填槽位，代码负责摆放**；浏览器 CSS 渲染→测量溢出→降级（缩字号→压缩该页→拆页）→测量坐标转 pptxgenjs | 调研 PPTAgent / Paper2Poster / Anthropic pptx skill，没人让模型直接输出坐标。App 本身在浏览器 iframe 里，可以直接用 CSS 测量，预览与导出同源 |
| J6 | **核验三级**：✅ 支持 / ⚠️ 部分 / ❌ 无出处；数字必须原样出现在**所引**证据中；区分 fact/summary/opinion | 有证据 ID ≠ 事实正确；核验能抓"引用不存在"和"数字对不上"，不能保证语义完全正确，README 要如实说明 |
| J7 | **AI 输出校验"宽进严出"** | 真实模型总有小偏差（多字段、超条数、重复键、少括号），严格拒收会白烧额度；但引用 ID 格式、数字、结构性错误必须守住 |
| J8 | **JSON 容错不用现成库** | 调研实测：jsonrepair 类库会把截断的数字"补全"成合法值（`80.` → `80`），在核验场景里会制造假事实 |

## 3. 平台事实（实测，2026-11-20）

- App = `manifest.json` + 静态 SPA，在受限 iframe 中运行（`connect-src 'self'`），不写 Executa。
- 当前平台分配模型：**`xiaomi/mimo-v2.5`**（openrouter）。App 无法指定模型。
- `llm.complete` 单次输出上限 8192；`responseFormat: json_object` **不生效**（仍返回代码块包裹的 JSON）。
- `llm.embed`：1536 维，**单次 ≤ 64 条**，**每次调用至少 1 额度**。
- 发布：开发者自助激活（已开通）→ App 已由 `anna-app dev --llm real` 自动创建：**`[DRAFT] paper2slides (id=288)`**。审核由用户联系 HR 处理，不是瓶颈。

## 5. 真实运行中遇到的问题与解决（按发现顺序）

> 每个问题都保存了模型原始输出作为回归测试 fixture（`src/llm/fixtures/`、`src/llm/real-output.test.ts`），并在 [prompts/README.md](../prompts/README.md) 记录迭代。

| # | 现象 | 根因 | 解决 | 额度损失 |
|---|---|---|---|---|
| P1 | 第一步"理解论文"失败：`modules[0]：含未定义字段…` | 校验用 `strictObject`，多一个字段就整份拒收；数组超长也拒收 | **T8 宽进严出**：丢弃未知字段、截断超长数组、合并重复模块、字段别名映射（`evidence_ids`→`evidenceIds`）；每次修正记入 `normalizations`；保存 `rawOutput` | 4.7 |
| P2 | 仍失败：`正文中未识别出可用于汇报的内容模块` | 模型在模块对象上**重复写 `kind` 键**：`{"kind":"problem","points":[…],"kind":"fact"}`。`JSON.parse` 保留**最后一个**值，6 个模块全被判无效 | 新增"首个键优先"解析（`src/llm/duplicate-keys.ts`）+ 记录 normalization；`understand` 提示词 v2 明确"模块只有 kind 和 points" | 2.3 |
| P3 | 第 4 页失败：`未找到格式正确的 JSON` | 模型输出完整 slide 但**少最后一个 `}`**（重试仍少） | 仅当文本以完整值结尾时补齐闭合符号；**停在数字中间绝不补**（防止制造假数字） | — |
| P4 | 第 3 页首次失败：`figureId：应为非空字符串` | 模型把 `figureId` 写进了 `slots` 里 | 自动上移到顶层并记录 | — |
| P5 | 测试失败（我推送过快） | 测试里硬编码了提示词版本号 | 改为不绑定版本号；之后坚持"全绿再推送" | — |
| P6 | 新提示词下封面失败：`slots.title：最多 60 个字符` | T9 把 60 字符的结论式标题限制也套到了封面；BERT 原题 80 字符 | 封面单独放宽到 180；`slide` 提示词 v3 | 3.5 |
| P7 | 用户反馈"质量不太高"（基于 Demo 导出） | Demo 假数据简陋；真实问题：内容浅、同一段引用复述、标题长且是模块名、图文不对应、讲稿空、页面下半空 | T9（内容）+ T10（视觉），见上表 | — |
| P8 | 用户问"为啥不动" | 后台脚本把输出缓冲到最后，看不到进度 | 改为日志实时写文件 + Monitor 推送进度，失败立即停止并保存原始输出和截图 | — |

## 7. 工作方式上的教训

- 用户要"商量"时不要直接开工（我在讨论阶段就装 CLI、生成骨架，被叫停）。
- 假数据测不出真实模型的偏差：**越早接真实模型越好**，每次失败都要保存原始输出做 fixture。
- 后台长任务必须有可见进度。
- 推送前跑全量测试。
